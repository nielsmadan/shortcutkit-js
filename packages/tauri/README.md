# @shortcutkit/tauri

Tauri host for `@shortcutkit/core`: a JSON state file that every window of the app shares, and system-wide global hotkeys. This directory holds both halves, the npm package `@shortcutkit/tauri` and the Rust crate `tauri-plugin-shortcutkit`. Pre-alpha; the API will change.

## Install

```bash
pnpm add @shortcutkit/core @shortcutkit/dom @shortcutkit/tauri
cargo add tauri-plugin-shortcutkit tauri-plugin-global-shortcut
```

ESM only, ES2023; needs Tauri 2. Install the same version of the three npm packages.

Register both plugins in the app's builder:

```rust
tauri::Builder::default()
    .plugin(tauri_plugin_global_shortcut::Builder::new().build())
    .plugin(tauri_plugin_shortcutkit::init())
```

Allow the plugin's commands in every capability whose windows use ShortcutKit, for example `src-tauri/capabilities/default.json`:

```json
{
  "identifier": "default",
  "windows": ["main"],
  "permissions": ["core:default", "shortcutkit:default"]
}
```

`shortcutkit:default` allows every command of the plugin, including `allow-sync-global-hotkeys`, which lets the webview register system-wide hotkeys without any `global-shortcut:*` permission. An app that wants less lists the individual permissions it needs instead: `shortcutkit:allow-load-state`, `shortcutkit:allow-save-state`, `shortcutkit:allow-sync-global-hotkeys`, `shortcutkit:allow-detach-global-hotkeys`, `shortcutkit:allow-global-hotkeys-state`, `shortcutkit:allow-keyboard-layout` and `shortcutkit:allow-system-shortcuts`, described in [`permissions/autogenerated/reference.md`](permissions/autogenerated/reference.md).

## Store

`tauriStore(options?)` is a `SyncedShortcutStore` backed by the plugin. Use one store per window for both the registry and `syncRegistry`:

```ts
import { createRegistry, defineContext, syncRegistry } from '@shortcutkit/core';
import { attachInput, detectPlatform } from '@shortcutkit/dom';
import { tauriStore } from '@shortcutkit/tauri';

const editor = defineContext({
  id: 'editor',
  actions: { save: { displayName: 'Save', defaults: 'mod+s' } },
});

const store = tauriStore();
const registry = await createRegistry({ contexts: [editor], platform: detectPlatform(), store });
syncRegistry(registry, store);
attachInput(registry);
```

Options:

- `file`: the state file's name, default `shortcuts.json`. It must match `^[a-z0-9][a-z0-9._-]*\.json$`, so it cannot point outside the state directory and two names cannot address one file on a case-insensitive file system; any other name is rejected by the plugin.
- `ipc`: a `TauriIpc` transport, default `defaultIpc()`, which wraps `@tauri-apps/api`'s `invoke` and the current webview's `listen`. Tests pass a fake.
- `logger`: receives warnings, default core's `consoleLogger`.

The file lives in the app's config directory, under the bundle `identifier` from `tauri.conf.json`:

| OS      | Directory                                       |
| ------- | ----------------------------------------------- |
| macOS   | `~/Library/Application Support/<identifier>/`   |
| Windows | `%APPDATA%\<identifier>\`                       |
| Linux   | `$XDG_CONFIG_HOME/<identifier>/` or `~/.config` |

To keep it elsewhere, configure the plugin with a directory:

```rust
.plugin(tauri_plugin_shortcutkit::Builder::new().directory("/path/to/dir").build())
```

How it behaves:

- Writes are atomic: the plugin writes a temporary file next to the state file, syncs it and renames it over the old one. The file is pretty-printed JSON with a trailing newline.
- A file that is not valid JSON is renamed to `<file>.corrupt-<unix-ms>` and loading fails with an error naming the backup. The registry then starts from its defaults, and its next save writes a fresh file without destroying the user's.
- Every save bumps a revision the plugin keeps in memory per file and announces it to every window. Each window re-reads the file when it learns of a newer revision than it has, and reports the state to `syncRegistry`. A write that lands while the window's own save is in flight, or between loading and subscribing, is picked up too.
- Last writer wins for the whole state. A window with unsaved edits refuses another window's state and saves its own over it.
- The plugin does not watch the file, so edits made outside the app are picked up only by a window that loads afterwards; open windows keep their state until their next save, which overwrites the edit.

## Global hotkeys

Actions in a context with `scope: 'global'` fire system-wide, even when the app is in the background. The plugin registers them with the OS through `tauri-plugin-global-shortcut`'s Rust API, so both plugins must be registered (see Install); without the global-shortcut plugin every global hotkey command fails with `tauri-plugin-global-shortcut is not registered`.

```ts
import { createRegistry, defineContext } from '@shortcutkit/core';
import { attachGlobalHotkeys } from '@shortcutkit/tauri';

const app = defineContext({
  id: 'app',
  scope: 'global',
  actions: { showWindow: { displayName: 'Show Window', defaults: 'ctrl+alt+meta+k' } },
});

const registry = await createRegistry({ contexts: [app, editor], platform, store });
registry.setGlobalHandler(app, (action) => {
  if (action === 'showWindow') void showMainWindow();
});
const hotkeys = attachGlobalHotkeys(registry);
```

A global context's actions run only through `registry.setGlobalHandler`; activating the context does nothing for them. `attachGlobalHotkeys(registry, options?)` returns `{ subscribe, getSnapshot, detach }`. Options: `ipc` and `logger` as for the store, and `systemShortcuts`, a provider whose `get()` lists shortcuts the OS reserves.

How it behaves:

- **Attach in every window.** Every window that renders a `<ShortcutRecorder>` must attach, because the plugin learns about recordings only from attachments.
- **One owner.** The first attachment owns the app's global hotkeys: the plugin registers the owner's bindings and emits presses to the owner's webview, where only the listener of the attachment whose id the press carries calls `registry.dispatchGlobal`. The emit is not private: a listener another script registers for any target, such as `listen` from `@tauri-apps/api/event`, also sees the presses. Other windows' bindings are not registered; with a shared store they are the same bindings anyway. When the owner detaches, its page reloads or its window is destroyed, the next attachment in attach order takes over and its bindings are registered.
- **Pause while recording.** While a recorder is recording in any attached window, none of the app's global hotkeys is registered, so pressing the current hotkey records it instead of firing it. They are registered again once no window is recording. `detach()`, a reload or closing the window ends that window's pause.
- **Only key presses.** A hotkey fires on key down only. Multi-step and mouse shortcuts cannot be global: they get the status `unsupported` and are not sent to the OS.
- **A modifier is required.** A global hotkey needs Ctrl, Alt, Shift or the meta key unless its key is `F1` to `F24`, so a bare letter or media key is not taken from every app; the plugin reports such a binding `failed` with `global hotkeys need a modifier`.
- **Syncs are coalesced.** Each registry change or recording change sends the current bindings once; an unchanged state sends nothing.
- `detach()` stops syncing and dispatching, removes its listeners and tells the plugin, unless this attachment never sent a sync the plugin may hold; it resolves once the plugin has answered, and failures are logged. A detach that removes nothing changes no state and announces nothing.

`getSnapshot()` returns `{ isOwner, paused, statuses }`. `statuses` maps `bindingKeyString(id)` (from `registry.globalBindings()`) to one of:

| Status             | Meaning                                                                                  |
| ------------------ | ---------------------------------------------------------------------------------------- |
| `pending`          | The plugin has not reported on this binding yet.                                         |
| `registered`       | The OS accepted the hotkey.                                                              |
| `shadowedBySystem` | Registered, but `systemShortcuts.get()` lists it, so the OS may take the key first.      |
| `failed`           | Registration failed; `error` says why, e.g. `registered elsewhere in the app`.           |
| `unsupported`      | `reason` is `multiStepInGlobal` or `mouseInGlobal`; the binding is never sent to the OS. |

When the sync command itself fails, for example without the global-shortcut plugin or the `allow-sync-global-hotkeys` permission, every binding that is not `unsupported` is `failed` with the command's error until a later sync succeeds. A failed registration is retried on the plugin's next change. The statuses are kept as they were while paused. A registration that succeeds does not prove the key will reach the app: macOS accepts `Cmd+Space` although Spotlight takes it.

The plugin registers and unregisters only its own shortcuts. Shortcuts the app registers itself through `tauri-plugin-global-shortcut` keep working, and a binding that collides with one registered earlier is reported as `failed` instead of taking it over. A catch-all `tauri_plugin_global_shortcut::Builder::with_handler` callback also receives ShortcutKit's presses and releases, so filter it down to your own shortcuts. Do not call the global-shortcut plugin's `unregisterAll` alongside ShortcutKit: it drops ShortcutKit's registrations without telling the plugin, which then reports them as registered.

## Menu accelerators

`syncMenuAccelerators(registry, bindings, options?)` keeps native menu items' accelerators in step with the registry, so the menu shows the user's current shortcuts. Build the menu with `@tauri-apps/api/menu` and pass the items:

```ts
import { Menu, MenuItem, Submenu } from '@tauri-apps/api/menu';
import { syncMenuAccelerators } from '@shortcutkit/tauri';

const save = await MenuItem.new({
  text: 'Save',
  action: () => registry.dispatch(editor, 'save'),
});
const menu = await Menu.new({ items: [await Submenu.new({ text: 'File', items: [save] })] });
await menu.setAsAppMenu();
const stop = syncMenuAccelerators(registry, [{ item: save, context: editor, action: 'save' }]);
```

Each item's accelerator comes from its action's first shortcut, set at start and whenever that string changes after a registry publish. Updates are serialized per item with the latest value winning, an unchanged value is not sent again, and a rejected `setAccelerator` is logged through `logger` without stopping the other items and sent again on the next registry publish. The returned function stops syncing and leaves the accelerators as they are.

`toAccelerator(shortcut, platform)` returns the string, or `undefined` when the shortcut cannot be a menu accelerator; the item's accelerator is then cleared. Only single-step key shortcuts qualify: the key must be a letter, digit, punctuation key, `Space`, `Tab`, `Enter`, `Backspace`, `Delete`, `Escape`, `Insert`, `Home`, `End`, `PageUp`, `PageDown`, an arrow, `F1` to `F24` or a numpad key, and a shortcut without modifiers must be an F-key or `Escape`. Modifiers come in the order `Ctrl`, `Alt`, `Shift`, then `Cmd` on macOS or `Super` on Linux; the meta key is not supported on Windows. Examples: `Shift+Cmd+KeyK` on macOS and `Ctrl+Shift+KeyK` on Windows for `mod+shift+k`.

Things to know:

- The menu item's `action` is yours: call `registry.dispatch(context, action)`. The accelerator only displays and triggers the item.
- When an active local context consumes the keydown in the page first, the menu item does not fire.
- Tauri has no way to read an accelerator back, and an unparseable accelerator is cleared silently by Tauri.
- `Super` on Linux is unverified: muda parses it as the meta modifier, and no Linux run has checked how it displays or triggers.
- Menus are not built by the plugin. On macOS the app menu is shared by every window, so build it once, from one window.

`predefinedMenuShortcuts(platform, items)` lists the accelerators Tauri's predefined menu items carry (`Copy`, `Cut`, `Paste`, `Undo`, `Redo`, `SelectAll`, `Minimize`, `Hide`, `HideOthers`, `CloseWindow`, `Quit`, `Fullscreen`) as core `MenuShortcut`s titled by the kind, omitting items that have none on that platform and items muda creates disabled there. Report collisions with the user's bindings through `registry.menuCollisions`:

```ts
const collisions = registry.menuCollisions([
  ...predefinedMenuShortcuts(registry.platform, ['Quit', 'Copy', 'Paste']),
  ...yourStaticItems,
]);
```

## Keyboard layout

`tauriLayoutMap(options?)` resolves a map from `KeyboardEvent.code` to the character the key types on the current layout, for `keyboardLayoutProvider` from `@shortcutkit/dom`. It returns `navigator.keyboard`'s map when the webview has one, otherwise the plugin's map, and `undefined` when neither has a map. It rejects when the plugin call fails, or when `getLayoutMap()` fails and the plugin has no map, so `keyboardLayoutProvider` warns once through its own `logger` and keeps the last good layout. Options: `ipc` as for the store.

```ts
import { keyboardLayoutProvider } from '@shortcutkit/dom';
import { tauriLayoutMap } from '@shortcutkit/tauri';

const layout = keyboardLayoutProvider({ load: tauriLayoutMap });
// <ShortcutKitProvider registry={registry} layout={layout}>
```

On macOS the plugin reads the current ASCII-capable layout through Carbon's `UCKeyTranslate` with no modifiers and no dead keys, so on an AZERTY layout `KeyQ` maps to `a`. The plugin has no native lookup elsewhere, so there the map comes from the webview's `navigator.keyboard.getLayoutMap()` (WebView2 has it) and webviews without it, such as WebKitGTK on Linux, fall back to the US layout. The provider refreshes on window focus, not when the layout changes.

## System shortcuts

`loadSystemShortcuts(options?)` resolves a `SystemShortcuts` provider holding the shortcuts macOS reserves: `get()` returns them as single-step core `Shortcut`s and `refresh()` reloads them, resolving `true` when the list changed. A failed lookup is logged through `logger`; the initial load then gives an empty list and a refresh keeps the old one. Pass `get` to `createRegistry` so system collisions show up in `registry.conflicts`, and to `attachGlobalHotkeys` for the `shadowedBySystem` status.

```ts
import { loadSystemShortcuts, watchSystemShortcuts } from '@shortcutkit/tauri';

const systemShortcuts = await loadSystemShortcuts();
const registry = await createRegistry({
  contexts,
  platform,
  store,
  systemShortcuts: systemShortcuts.get,
});
const stop = watchSystemShortcuts(registry, systemShortcuts);
```

`watchSystemShortcuts(registry, systemShortcuts, { target? })` refreshes on `focus` of `window` (or `target`) and calls `registry.refreshConflicts()` when the list changed; it returns a function that stops watching.

On macOS the plugin reads the enabled entries of System Settings > Keyboard > Keyboard Shortcuts through Carbon's `CopySymbolicHotKeys`, keeping those with at least one of Cmd, Shift, Option or Control and a key the plugin can name. App-specific and third-party global hotkeys are not reported. Elsewhere the list is empty.

## Rust API

```rust
pub fn init<R: Runtime>() -> TauriPlugin<R>;
pub struct Builder;
impl Builder {
    pub fn new() -> Self;
    pub fn directory(self, dir: impl Into<PathBuf>) -> Self;
    pub fn build<R: Runtime>(self) -> TauriPlugin<R>;
}
```

`init()` is `Builder::new().build()`. Without `directory`, the plugin uses `app.path().app_config_dir()`.
